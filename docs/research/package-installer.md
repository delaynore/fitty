# Установка обновлений Fitty на Android 14–16

Для Fitty стоит перейти на `PackageInstaller.Session` ради статусов установки и восстановления попытки после перезапуска. Срочности из-за Android 14–16 нет. Android пометил `ACTION_INSTALL_PACKAGE` устаревшим в API 29, а в исходниках AOSP для всех трёх версий есть обработчик этого действия. Системное подтверждение нужно сохранить согласно сценарию Fitty. Выводы основаны на коде и документации. Установку на устройствах в рамках исследования не запускали. [Контракт Android](https://developer.android.com/reference/android/content/Intent#ACTION_INSTALL_PACKAGE) · [AOSP 14](https://android.googlesource.com/platform/frameworks/base/+/android-14.0.0_r1/packages/PackageInstaller/src/com/android/packageinstaller/InstallStart.java) · [AOSP 15](https://android.googlesource.com/platform/frameworks/base/+/android-15.0.0_r1/packages/PackageInstaller/src/com/android/packageinstaller/InstallStart.java) · [AOSP 16](https://android.googlesource.com/platform/frameworks/base/+/android-16.0.0_r1/packages/PackageInstaller/src/com/android/packageinstaller/InstallStart.java) · [Сценарий обновления Fitty](../app-updates.md)

## Что происходит в `488e0a2`

- `AndroidUpdateInstaller` проверяет доверие к Fitty как к источнику установки через `canRequestPackageInstalls()`. При необходимости он открывает `ACTION_MANAGE_UNKNOWN_APP_SOURCES`. Для установки он выдаёт системной Activity доступ на чтение `content://` URI через `FileProvider` и просит прислать код результата. Успех вызова launcher означает, что Fitty передал запрос системе. [Установщик Fitty](../../app/src/main/java/com/delaynore/fitty/data/updates/AndroidUpdateInstaller.kt) · [Проверка разрешения](https://developer.android.com/reference/android/content/pm/PackageManager#canRequestPackageInstalls())
- `UpdateInstallerEffect` открывает настройки разрешения или установщик только на видимом экране настроек Fitty при `RESUMED`. `UpdateCoordinator` удаляет APK по возврату из установщика и различает `RESULT_OK`, `RESULT_CANCELED` и прочие коды. В AOSP `RESULT_CANCELED` встречается и при остановке на входе в установщик, поэтому одного кода недостаточно, чтобы приписать отказ пользователю. Fitty не читает детали результата из возвращённого `Intent`. [Эффект](../../app/src/main/java/com/delaynore/fitty/ui/settings/UpdateInstallerEffect.kt) · [Координатор](../../app/src/main/java/com/delaynore/fitty/ui/settings/UpdateCoordinator.kt) · [Вход в установщик AOSP 16](https://android.googlesource.com/platform/frameworks/base/+/android-16.0.0_r1/packages/PackageInstaller/src/com/android/packageinstaller/InstallStart.java) · [Результат ошибки в AOSP 16](https://android.googlesource.com/platform/frameworks/base/+/android-16.0.0_r1/packages/PackageInstaller/src/com/android/packageinstaller/InstallFailed.java)
- `AppContainer` сохраняет путь к APK только на время выдачи разрешения. Если Android пересоздаст процесс во время установки, новый координатор может получить результат Activity без соответствующего состояния `Installing` и проигнорировать его. После самообновления надёжная проверка результата при следующем запуске состоит в чтении установленного `versionCode`. Android также отправляет обновлённому приложению системное событие `ACTION_MY_PACKAGE_REPLACED`. [Контейнер](../../app/src/main/java/com/delaynore/fitty/AppContainer.kt) · [Координатор](../../app/src/main/java/com/delaynore/fitty/ui/settings/UpdateCoordinator.kt) · [Событие замены пакета](https://developer.android.com/reference/android/content/Intent#ACTION_MY_PACKAGE_REPLACED)

## Как перейти на сессию

**Манифест.** Оставить `REQUEST_INSTALL_PACKAGES` и запрос доверия к Fitty как к источнику APK. Добавить `BroadcastReceiver` с `android:exported="false"` для статусов сессии. Адресовать `PendingIntent.getBroadcast()` явно этому компоненту и отличать попытки по `sessionId` в идентичности `PendingIntent`, например по `requestCode`. На API 31+ задать `FLAG_MUTABLE`, чтобы Android мог добавить статус и подтверждение, а на API 26–30 оставить старую семантику изменяемости. На Android 14 при `targetSdk >= 34` изменяемый `PendingIntent` с неявным `Intent` запрещён. На Android 15+ `commit()` при `targetSdk >= 35` выбрасывает исключение для неизменяемого получателя. Один получатель нужен и для промежуточного, и для итогового статуса. Если все установки перейдут на сессии, удалить `UpdateFileProvider` и `update_file_paths.xml`: установщик получает байты из сессии. [Манифест Fitty](../../app/src/main/AndroidManifest.xml) · [Изменения Android 14](https://developer.android.com/about/versions/14/behavior-changes-14#safer-intents) · [Контракт commit](https://developer.android.com/reference/android/content/pm/PackageInstaller.Session#commit(android.content.IntentSender))

**`AndroidUpdateInstaller`.** Ввод-вывод вынести с главного потока. Создать сессию `MODE_FULL_INSTALL`, скопировать проверенный APK через `openWrite()`, вызвать `fsync()`, закрыть поток и вызвать `commit()`. При ошибке подготовки закрыть ресурсы и удалить незавершённую сессию через `abandon()`. Базовые методы сессии доступны с API 21, поэтому на API 26–28 отдельный установщик не нужен. На API 31+ задать `USER_ACTION_REQUIRED` явно. Платформа допускает отдельный сценарий самообновления с `USER_ACTION_NOT_REQUIRED`, `UPDATE_PACKAGES_WITHOUT_USER_ACTION` и минимальным target SDK устанавливаемого APK 31, 33 и 34 соответственно на Android 14, 15 и 16. Fitty по продуктовому контракту просит подтверждение. Совпадение идентификатора приложения и ключа подписи остаётся условием замены. [Сессия](https://developer.android.com/reference/android/content/pm/PackageInstaller.Session) · [Условия подтверждения](https://developer.android.com/reference/android/content/pm/PackageInstaller.SessionParams#setRequireUserAction(int)) · [Решение о публикации Fitty](../adr/0001-distribute-app-updates-through-github-releases.md)

**`UpdateCoordinator`.** Заменить `Installing(apk)` и обработку кода Activity на состояния подготовки, ожидания подтверждения и ожидания итогового статуса, привязанные к `sessionId`. До `commit()` сохранить запись о попытке с `sessionId` и ожидаемым `versionCode` в постоянном хранилище. Получатель должен иметь возможность записать итог без открытой Activity. Применять события только к текущей попытке и принимать дубликаты без повторных действий. `STATUS_SUCCESS` завершает попытку, `STATUS_PENDING_USER_ACTION` приносит системный `Intent` в `Intent.EXTRA_INTENT`, а `STATUS_FAILURE_*` передают причины отказа. Например, `STATUS_FAILURE_ABORTED` означает прерывание, в том числе отказ пользователя или отказ самой программы от сессии. При старте сверять установленный `versionCode`, сохранённый итог и `getSessionInfo()`. Если версия не обновилась, сессия исчезла и итог не был записан, показать возможность повторить попытку с неизвестным итогом. При восстановлении сессии продолжать подтверждение, только если есть действующий системный `Intent`. Если восстановить подтверждение невозможно, нужен явный путь завершить старую попытку и повторить. Исходный APK нужен, пока Fitty ждёт разрешение и копирует файл. После успешного `commit()` сессия владеет копией, а Fitty может удалить исходный файл. Стартовая чистка кэша должна учитывать сохранённую попытку. [Контракт статусов и сведения о сессии](https://developer.android.com/reference/android/content/pm/PackageInstaller) · [Запись и завершение сессии](https://developer.android.com/reference/android/content/pm/PackageInstaller.Session) · [Кэш Fitty](../../app/src/main/java/com/delaynore/fitty/data/updates/UpdateApkCache.kt)

**`UpdateInstallerEffect`.** Сохранить launcher для разрешения и повторную проверку `canRequestPackageInstalls()` по возврату. Когда координатор получит `STATUS_PENDING_USER_ACTION`, открывать переданный Android `Intent` один раз на конкретный запрос подтверждения, при видимых настройках и `RESUMED`. Если пользователь ушёл с экрана, отложить открытие до возврата. Возврат из окна подтверждения может служить сигналом для UI, итог установки приходит получателю сессии. Сам получатель не должен открывать Activity из фона. Android 14 и 15 ужесточили правила фоновых запусков через `PendingIntent`, а Android 16 добавил диагностику таких запусков в StrictMode. [Подтверждение установки](https://developer.android.com/reference/android/content/pm/PackageInstaller#STATUS_PENDING_USER_ACTION) · [Правила запуска Activity](https://developer.android.com/guide/components/activities/secure-bal)

## Что проверить на устройстве при реализации

Пройти обновление между двумя подписанными сборками с данными предыдущей версии на Android 14, 15 и 16. Проверить отказ в разрешении источнику, выдачу разрешения после возврата, отмену подтверждения, ошибку подписи, уход с настроек до подтверждения, пересоздание Activity и гибель процесса на этапах подготовки и ожидания подтверждения. После успешной замены сверить новый `versionCode`, выбранную программу, текущую тренировку с записанными подходами и историю. Проверить, что повтор не оставляет сессию и APK от предыдущей попытки. На Android 8 отдельно достаточно пройти выдачу разрешения, подтверждение и успешную установку для проверки нижней границы API.
